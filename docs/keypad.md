# UV-K10 Pro 按键矩阵、编码和事件状态机

本页仅分析 **`K10PRO_ENG_v8.02.16`** 官方应用固件。样本解包后映射到
`0x08002000`，SHA-256 为
`061759672cc69a1b00420ce6fae67b0756d3db111f8fa4329cadc940dcd17f17`。
没有套用 UV-K1、UV-K5、UV-K6 或其他机型的按键编号。文中的函数地址是这一
样本的复现锚点，不是原厂源代码符号。

已恢复的结构为 **19 个矩阵扫描位置 + 3 个独立低电平输入 + 独立 PC13/PTT**。
普通扫描函数只返回一个最高优先级键码；PC13 在上层轮询函数中独立处理。
这里确认的是 MCU 端口位及固件行为，**没有将它们冒充为 MCU 封装脚号、PCB
测试点、按键排线针序或已实测电路图**。

所有数字键、菜单、返回、方向键与 A/B 选择的主要语义均有原厂函数执行证据。
其余键的功能可由分支追踪，但键帽完整文字、侧键物理上下顺序和 PCB 隔离元件
仍须 K10 Pro 实机照片或通断测量闭环。

脚本 [emulate_keypad.py](../tools/emulate_keypad.py) 使用公共
[StockEmulator](../tools/emulate_stock.py)。已经执行的 **53 个案例**记录在
[keypad-analysis.json](evidence/keypad-analysis.json)：30 个原始扫描案例、10 个
过滤状态机案例、11 个 UI 数据流案例和 2 个延时单位案例。

```sh
python -m pip install -r requirements-re.txt
python tools/emulate_keypad.py /path/to/K10PRO_ENG_v8.02.16.raw.bin \

```

测试未携带原厂固件。不提供样本时，原厂函数重放测试会跳过；独立构造的测试
仍检查未知 GPIO 访问、未初始化输入和未建模电气冲突会明确失败。

仿真没有运行整个系统、实际设备、安卓 APK 或 PC 程序。输入为明确指定的
接点闭合状态，事件输出在进入 RF/UI 副作用之前截获。UI 数据流实验直接调用
主界面或菜单函数，不声称已经重放完整屏幕、通话或调度器。

## 2. GPIO 定义与初始化

端口基址来自官方 PY32F071 CMSIS 定义：GPIOA `0x50000000`，GPIOB
`0x50000400`，GPIOC `0x50000800`，GPIOF `0x50001400`。[Puya CMSIS][cmsis]
GPIO 初始化结构和常数另与 [OpenPuya 的 PY32F071 LL GPIO 头文件][ll-gpio]
核对；读取时文件 blob SHA 为 `3e7ec83ddb91f78fecda44c0250b4ace59e99633`。

| 角色 | MCU 端口位 | GPIO 配置 | 空闲 / 有效电平 |
| --- | --- | --- | --- |
| 矩阵行 0 | PF8 | 输出、推挽、上拉、speed=3 | 空闲高，扫描选中时低 |
| 矩阵行 1 | PB4 | 同上 | 同上 |
| 矩阵行 2 | PB3 | 同上 | 同上 |
| 矩阵行 3 | PA14 | 同上 | 同上 |
| 矩阵列 0 / 专用键 24 | PB15 | 输入、上拉 | 低有效 |
| 矩阵列 1 / 专用键 23 | PB14 | 输入、上拉 | 低有效 |
| 矩阵列 2 / 专用键 25 | PB13 | 输入、上拉 | 低有效 |
| 矩阵列 3 | PB12 | 输入、上拉 | 低有效 |
| 矩阵列 4 | PA8 | 输入、上拉 | 低有效 |
| 独立 PTT 输入 | PC13 | 输入、上拉 | 低有效 |

原厂初始化先通过 BSRR 将四条行输出锁存器置高，再切换为输出模式。
实际重放的每条行配置都是：

```text
MODER = 1, OTYPER = 0, OSPEEDR = 3, PUPDR = 1, ODR = 1
```

`OTYPER=0` 是推挽，不是开漏；speed=3 是 SDK 的
`LL_GPIO_SPEED_FREQ_VERY_HIGH` 档位，不是“扫描频率 3 MHz”。列与 PC13 的
`MODER=0`、`PUPDR=1`。仿真的输入引脚 OSPEEDR=0 来自合成初始寄存器为零，
原厂输入初始化不修改该字段，不能把它描述成原厂给输入指定了速度。

`0x08018B94` 同时初始化 NOR、接收器和 RF 总线等其他 GPIO，**不要把整个
函数的 PA/PB/PF 掩码照抄到独立键盘驱动**。例如原厂该函数还把 PA13 设为
输出；它不是这里恢复的矩阵行。

### PA14 与调试接口

PY32F071 的 PA14 还具有 SWCLK 功能，见[数据手册端口 A 复用表][datasheet]。
将 PA14 切到键盘行输出会占用 SWCLK。独立诊断固件因此默认
`K10_ENABLE_KEYPAD=0`；显式启用前需要了解此引脚复用。这里没有更改选项字节，
也没有把恢复 MCU 端口位等同于已经确定调试焊盘。独立 PC13 输入只用于记录
按下/释放，不直接接通发射。

## 3. 矩阵原始编码

表中数字是原厂返回的十进制 key code，不是按键的物理行列编号。列顺序就是
每次扫描的读取优先级。

| 拉低的输出行 | PB15 | PB14 | PB13 | PB12 | PA8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| PF8 | 17 | 1 | 4 | 7 | 10 |
| PB4 | 12 | 2 | 5 | 8 | 11 |
| PB3 | 13 | 3 | 6 | 9 | **本行不读取此列** |
| PA14 | 18 | 14 | 0 | 15 | 16 |

PB3/PA8 是扫描表中缺少的第 20 个格子。仿真将这一接点闭合，原厂仍返回
`0xFF`；这只证明固件没有读取该格，不能证明 PCB 上绝无焊盘或其他用途。

所有行置高时，扫描器先进行三个低电平检测：

| 检测优先级 | 输入 | 返回代码 | 固件选择的配置字段 |
| ---: | --- | ---: | --- |
| 1 | PB15 | 24 / `0x18` | `0x200023F1` 短按，`0x200023F2` 长按 |
| 2 | PB14 | 23 / `0x17` | `0x200023F3` 短按，`0x200023F4` 长按 |
| 3 | PB13 | 25 / `0x19` | `0x2000240E` 短按，`0x2000240F` 长按 |

这符合“独立按钮把列输入拉低”的逻辑拓扑。单靠固件不能区分其间的串联电阻、
二极管、缓冲元件或 PCB 路由。设置映射的相关位置为 `0x13011..14` 与
`0x1302E..2F`，见[设置研究](settings-map.md)；侧键 1/2/3 的产品标签还必须
结合经过型号审计的官方软件路径，物理上中下位置须另行验证。本轮 K8 分支审计
已经完成：这些字段依次标为侧键1（24）、侧键2（23）、侧键3（25）；独立驱动的
`SK1/SK2/SK3` 标签只表达该设置对应关系，不宣称已经确认机壳顺序。

### 完整扫描顺序

1. 读取 `0x2000000A`。若不等于 `0xFF`，直接返回该值，不访问 GPIO。
   这是软件覆盖入口；本研究未确定其所有写入来源，不将它当作实体按键。
2. 四条行全部置高；读取 PB15、PB14、PB13，检测上述独立键。
3. 按 PF8 → PB4 → PB3 → PA14 顺序，每次拉低一条行，依照矩阵表读取列。
4. 命中第一个低电平就选择对应代码；无命中返回 `0xFF`。
5. 正常硬件扫描返回前把四条行恢复为高。软件覆盖分支不触碰 GPIO，因此
   保留调用前的状态。

没有按键时，真实代码读取 GPIO 共 22 次：3 次专用键检测加 19 个矩阵位置。
空闲路径调用八次 `delay_us(1)`；不同的提前命中路径会减少读取与延时次数。

仿真确认 `(1,4)` 同时按下返回 1，分处不同扫描行且不同列的 `(4,2)` 返回 4，
专用键 24 与矩阵键 1 同时按下返回 24，三个专用键同时低时返回 24。这是
单码扫描的**软件优先级**，不是多键无冲突能力的证明。

推挽行在多键组合下可能需要板上隔离元件才能避免电气冲突。模型主动拒绝
“两条行同时通过闭合接点连接同一列”和“矩阵与专用键同时闭合同一列”；
未推测真实电流、鬼键、二极管方向或全键无冲突能力。

## 4. 键码到 UI 动作

| 代码 | 可采用的逻辑名称 | 证据及名称边界 |
| ---: | --- | --- |
| 0–9 | 数字 0–9 | `0x08006EF4` 对代码直接加 `0x30`；实际返回 ASCII 数字；数字输入分支把这些数值按十进制累加 |
| 10 | A/B 选择 | `0x08009CB4 → 0x08009F0C` 翻转当前主显示/主信道选择字节 `0x200023E0`；两个方向已重放 |
| 11 | 信道 / VFO 模式切换 | `0x08009FB0` 根据当前记录类型，在已保存信道和 VFO 索引之间切换；静态数据流，未将键帽文字写成已拍照确认 |
| 12 | 上 / 上一项 | 菜单处理向 `0x08005DF0` 传 `-1`；真实菜单索引 2 → 1 |
| 13 | 下 / 下一项 | 同一路径传 `+1`；真实菜单索引 2 → 3 |
| 14 | 星号 / 手动拨号、长按扫描功能 | 信令 profile 0 输出 `*`；主界面 `0x0800A6CC` 短释放进入手动拨号输入，长按走 `0x0800E018(0)`；完整键帽文案未确认 |
| 15 | 功能 / 井号 / 键盘锁 | 信令 profile 0 输出 `#`；`0x0800C480` 短释放设置功能前缀，长按翻转锁字节 `0x200023E4`；锁定/解锁均已重放 |
| 16 | 频段选择 | `0x08009E0C` 在 VFO 类记录中增加频段索引，交给 `0x08007350` 校验后写回；静态追踪 |
| 17 | MENU / 进入 / 确认 | 主界面请求 UI state 2；菜单深度 0 → 1；实际分支重放 |
| 18 | EXIT / 返回 / 退格 | 菜单深度 1 → 0，顶层请求回 UI state 0；编辑分支删除输入；实际菜单返回重放 |
| 21 | PTT | 由 PC13 独立生成，进入 `0x0800A4A4` 按下/释放业务路径；不由矩阵扫描产生 |
| 23/24/25 | 可配置专用键 | 由上一节对应配置选择短/长动作；按键帽 / 机壳位置暂不强行命名 |
| `0xFF` | 无键 | 扫描结束无低电平命中 |

代码 19、20、22 没有被此扫描器产生。不能将代码最大值 25 解释成“有 26 个
实体按钮”。信令字符表还依赖 profile 参数；某个按键在 DTMF 中代表 A/B/C/D，
也不意味着键帽就印有对应字符。

### 事件参数不是“点击次数”

`0x080082FC(key, pressed, held)` 的后两个参数表达按下状态和长按状态：

| 事件 | pressed | held | 应用处理注意 |
| --- | ---: | ---: | --- |
| 稳定按下 | 1 | 0 | 菜单/方向等键可立即处理 |
| 短按释放 | 0 | 0 | 专用键、功能前缀等在这里执行短动作 |
| 长按成立或重复 | 1 | 1 | 执行长动作或连续调节 |
| 长按后的释放 | 0 | 1 | 不应再次当作短动作 |

`0x0800C2E0` 对 23/24/25 的首次按下主要请求提示反馈；短功能字节在 `(0,0)`
执行，长功能字节在 `(1,1)` 执行，`(0,1)` 不再次执行短功能。这一差异应保留在
任何希望兼容原厂交互的上层键处理器中。

## 5. 去抖、长按和重复

主要状态地址：

| RAM | 含义 |
| --- | --- |
| `0x200000D2` | 上一次原始样本 |
| `0x200000D3` | 当前已确认键 |
| `0x200000D0`，16 位 | 相同样本连续计数 / 持续计数 |
| `0x20000200` | 已产生长按状态 |
| `0x20000201` | 已确认 PTT 状态 |
| `0x20000202` | PTT 去抖计数 |

新原始样本与上次不同，写入候选键并把计数清零；之后每次样本相同才递增。
计数等于 4 时确认变化，所以从第一次看到变化算起，需要 **5 次连续观察**。
四次后又松开不会产生按下事件。键 A 稳定切换为键 B 时，状态机先发 A 的
释放，再发 B 的按下；不是直接覆盖旧键而漏掉释放。

计数等于 128 时，允许长按的键产生 `(key,1,1)`。允许集合为：
`0..9, 12, 13, 14, 15, 17, 23, 24, 25`。因此在合成实验中，第一轮发现按下，
第 5 轮发普通按下，第 **129** 轮才发长按。10、11、16、18 不在该长按集合中。

计数大于 128 后，12、13 每 16 次相同样本产生重复；应用 state=1 时，5–8
还具有同样的重复路径。重放事件发生于第 145、161 轮。16 位计数达到 `0xFFFF`
时回置 128，以保持长期持有的处理状态。释放事件保留 held 标志；例如数字 1
经过长按后释放得到 `(1,0,1)`。

这些是扫描过滤器产生的事件，不代表所有 UI 模式都会对每个事件采取动作。
应用派发中还存在键盘锁、不同工作模式、输入框和业务状态过滤。

### PC13/PTT 的独立去抖

PC13 持续低 5 轮产生 `(21,1,0)`；已经按下时，持续高 2 轮产生 `(21,0,0)`。
相反电平在阈值前出现会清除相应计数。PTT 不走矩阵长按/重复集合。

PC13 和矩阵同一轮达到按下阈值时，实际代码先派发 PTT，再派发矩阵按下。
PTT 释放时如果还有矩阵稳定键，代码还会写 `0x200000D5=1`，供应用层抑制
相关后续动作。上层处理可能再次改变 PTT 状态，例如进入不允许通话的 UI 模式；
不能仅凭低层输入状态推断收发机当前处于发射。

## 6. 扫描延时与名义轮询周期

已单独执行原厂 `0x0801A520`，以 **合成 72 MHz 软件时钟值**为输入，观察到：

| 项目 | 原厂算式 / 实验值 |
| --- | --- |
| SysTick LOAD | `clock / 100 - 1`，合成结果 `719999` |
| SysTick CTRL | `7`，使用内核时钟、使能计数和中断 |
| `0x2000003C` | `clock / 1,000,000`，合成结果 `72` |
| `0x0801D010(1)` | 等待 VAL 累计差至少 72 个计数，设计单位为 1 µs |
| `0x0801D000(1)` | 参数先乘 1000；实验等待 72000 个计数，设计单位为 1 ms |

合成计数器每次读取向前推进 72 个计数，用于验证算式与单位；它没有测量目标
CPU 的指令耗时。因此扫描中的 `delay(1)` 可命名为**名义微秒延时**，不能说
真实板上的每段间隔恰好是 1 µs。

向量表的 SysTick 项为 `0x0801BA71`。该 handler 置 `0x20000014=1`；主循环
`0x0801D2E6` 消费该标志，调用 `0x0800C628`，后者在 `0x0800C9BA` 调用
按键过滤器 `0x08008A14`。设计节拍因此是 100 Hz，即名义 10 ms 一轮。
标志是一个字节而非积累计数，主循环阻塞时多个 tick 可以合并，所以实际轮询
间隔可能更长。

在不丢轮询的理想情况下，普通键的五次观察对应约 40–50 ms 的相位相关确认
时间，长按从初次采样到成立约 1.28 s，重复间隔约 160 ms。PC13 释放采用两次
观察，对应约 10–20 ms。可复现的严格结论是上面的**轮次数和计数阈值**，不是
硬件实测时间保证。

独立固件可以采用明确的基于时间的去抖和长按策略；若其阈值与这些原厂计数
不同，应记录为独立交互设计，而不是宣称已经复制原厂时序。

## 7. 剩余硬件确认项

- MCU 型号可以与 PY32F071 对齐，但只有看到封装后才能将 PA/PB/PC/PF 映射到
  本机对应封装的数字脚号；不能跨 LQFP/QFN/CSP 直接套用。
- 19 个矩阵接点的键帽字样、3 个侧/专用键的机壳位置，需要 K10 Pro 专属的
  清晰照片或连续性测量。软件标签和物理位置是两个证据层。
- 推挽扫描下的隔离二极管、串联电阻和组合键电气行为尚未建模；本次优先级
  实验不证明真实硬件可以安全支持任意组合。
- 软件覆盖字节 `0x2000000A` 的全部来源、特殊 UI 状态过滤和应用层按键重映射
  尚未全部枚举；这不影响已经执行验证的原始 GPIO 矩阵。
- 这里只恢复输入，不构成发射控制、射频参数正确性或实机刷写成功的验证。
